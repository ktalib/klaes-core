# CSV Importer Migration Analysis & Implementation Plan

## 1. Objective & Outcome
- **Goal**: Migrate the FastAPI-based importer in `csvimporter/main.py` to Laravel while preserving every data validation rule, multi-table write, and workflow guardrail that currently exists.
- **Success**: Laravel commands, services, and UI endpoints mirror the PRA, PIC, File History, File Indexing, and File Number imports so downstream systems (prop ID master, grouping tables, CofO history) continue to function without rework.

## 2. Current Python Workflow Map
| Workflow | Entry Point(s) | Key Helpers | Primary Tables Observed |
| --- | --- | --- | --- |
| File Indexing | `@router.post("/file-indexing/*")` in `app/routers/file_indexing.py` plus `process_file_indexing_data()` in `csvimporter/main.py` | `_assign_property_ids`, `_build_grouping_preview`, `_run_qc_validation`, `_apply_ui_date_format_to_session_records` | `FileIndexing`, `FileNumber`, `Grouping`, `CofO`, staging previews (in memory) |
| File Number Import | `app/routers/file_number_import.py` | `_serve_doc_file`, `_strip_all_whitespace`, QC helpers | `FileNumber`, file-number specific audit tables |
| PRA & PIC Imports | Currently share utility layer in `app/services/file_indexing_service.py` and staging helpers in `app/services/staging_handler.py` even if routers are being consolidated | `_build_cofo_record`, `_classify_customer_type`, `_generate_tracking_id`, `_has_cofo_payload` | `CofO`, `FileNumber`, `entities_staging`, `customers_staging`, `prop_id master` |
| File History | `app/routers/file_history.py` | `_parse_file_history_date/time`, `_is_cofo_indicator`, staging helpers | `file_history` staging tables, CofO appenders, transaction logs |
| Duplicate QC | `app/routers/duplicate_qc.py` | `_normalize_file_number_for_match`, `_grouping_match_info` | QC report tables, `Grouping` |

> **Observation**: Nearly all flows eventually depend on `_assign_property_ids`, `_generate_tracking_id`, and `_build_cofo_record`, so the Laravel migration must first reproduce these shared services before any individual importer can move.

## 3. Analysis Backlog (Python → Laravel Knowledge Capture)
1. **CSV Input Normalization**
   - Inventory column mappings (`process_file_indexing_data()` field map, PRA/PIC schema expectations) and confirm whether casing/spacing normalization happens per-importer or centrally.
   - Document numeric coercion rules (`numeric_like_fields`, `_normalize_numeric_field`) and datetime parsing fallbacks (SQL Server min/max guardrails).
   - Pull canonical file-number patterns, category codes, and sample sequences from `folder_watcher/static/correct_fileno.json` so Laravel QC mirrors every known variant.
2. **Database Touchpoints**
   - Map every ORM call from `FileIndexing`, `FileNumber`, `Grouping`, `CofO`, `prop_id` helpers, and staging handlers. Capture insert/update ordering and transactional boundaries (e.g., `_build_cofo_record` relies on `_combine_location` before commit).
   - Reverse-engineer the property ID system from `_assign_property_ids` + `_get_next_property_id_counter` for Laravel’s `PropIdService`.
3. **Validation & QC**
   - Catalogue QC buckets (`padding`, `year`, `spacing`) generated by `_run_qc_validation`.
   - Note contextual validation such as `_check_padding_issue`, `_normalize_registry`, `_canonical_reason_retired`.
   - Identify fast-fail raising points (`HTTPException` surfaces) vs. soft warnings stored in session.
4. **Session & Preview Mechanics**
   - Understand how FastAPI stores upload sessions (`app.sessions`) and how previews are built for UI consumption (e.g., `_apply_ui_date_format_to_session_records` mutating session payloads).
   - Determine retention expectations (in-memory only vs. persisted) so we can decide between Laravel cache, Redis, or DB-backed staging tables.
5. **File Number Governance**
   - Confirm rule: only File Number imports touch `file_number` tables (explicit in requirements and enforced by router separation).
   - Track how grouping lookups gate writes to `awaiting_fileno` fields.
6. **Error Handling / Rollback**
   - Identify where `SessionLocal` transactions are started/committed, and whether partial failures roll back multi-table writes.
   - Capture how CSV parsing errors bubble to UI (exceptions vs. validation arrays).

Deliverable: annotated diagrams and notes stored alongside this plan (link back to `csvimporter/DOCUMENTATION_INDEX.md` for cross-references).

## 4. Laravel Migration Strategy
### Phase 0 – Foundation
1. **Laravel Module Skeleton**
   - Create a `CsvImporter` domain module containing: console commands, service classes, form requests, jobs, observers, and dedicated tests.
   - Configure database connections/aliases that mirror SQL Server schemas used by FastAPI (may require SQL Server driver setup in Laravel’s `config/database.php`).
2. **Shared Services Port**
   - Re-implement `_normalize_*`, `_format_*`, `_assign_property_ids`, `_generate_tracking_id`, `_canonical_reason_retired`, `_build_cofo_record` as Laravel service classes with unit tests.
   - Provide facades or dependency-injected services so each importer command can reuse identical logic, while ensuring tracking metadata is sourced from grouping lookups during the mapping step rather than from the indexing workflow payload.

### Phase 1 – Analysis & Parity Verification
1. Finish the backlog in Section 3 and produce:
   - Table relationship diagram (prop IDs ↔ FileNumber ↔ Grouping ↔ CofO).
   - CSV schema dictionary for PRA, PIC, File History, File Indexing, File Number templates.
2. Review SQL scripts in `database_scripts/` for existing triggers or stored procedures that might fire during imports.
3. Decide on queue strategy (sync vs. queued jobs) and document expected throughput.

### Phase 2 – Laravel Infrastructure
1. **Commands & Jobs**
   - Implement Artisan commands (e.g., `csv:import:file-indexing`, `csv:import:pra`, etc.) that accept file paths or ingest from storage.
   - Wrap heavy work in queued jobs with progress tracking for UI surfaces (leveraging Laravel Broadcasting or notifications).
2. **Validation Layers**
   - Use custom `FormRequest` classes and validator rules mirroring `_run_qc_validation` plus CSV schema checks.
   - For QC suggestions (padding/year spacing), emit structured feedback entities saved to a `qc_findings` table for UI.
3. **Transactions & Locking**
   - Wrap multi-table writes in `DB::transaction()` and implement row-level locking for prop ID counter increments (e.g., `SELECT ... FOR UPDATE` equivalent).
   - Ensure file number imports check authorization guard (see Section 5) before mutating `file_number` tables.

### Phase 3 – Workflow Ports
1. **File Indexing**
   - Port pandas-based normalization to Laravel (use `league/csv` + custom normalizers or integrate a lightweight Python bridge only if necessary).
   - Build grouping preview repository that mirrors `_build_grouping_preview`, caching lookups to minimize SQL load.
2. **File Number Import**
   - Expose file-number-only write path with the same `_check_padding_issue`, `_check_year_issue`, `_check_spacing_issue` logic powered by the catalog dataset in `folder_watcher/static/correct_fileno.json` (seed validators and fixtures from it).
   - Serve documentation assets (`FILE_NUMBER_IMPORT.md`, mapping files) via Laravel controllers/storage.
3. **PRA/PIC/File History**
   - Implement staging ingestion service that writes to `entities_staging` and `customers_staging` only from these flows, preserving the `reason_retired` mapping.
   - Replicate `_parse_file_history_date/time`, `_is_cofo_indicator`, and CofO enrichment steps so CofO rows stay synchronized.
4. **Duplicate QC**
   - Create an API route (`/api/duplicate-qc`) backed by Eloquent queries that mimic `_grouping_match_info` semantics and canonicalization.

### Phase 4 – UI & Workflow Integration
1. Build or extend Laravel Blade/Inertia pages that align with current templates (`file_indexing.html`, `file_history_import.html`, etc.), including staging previews and QC tables.
2. Connect with the existing KLAES file indexing module by:
   - Publishing events/webhooks after successful imports.
   - Enforcing RBAC so only System Admin users (and automation acting on their behalf) can access any import module or trigger file-number writes.
3. Implement monitoring/logging (Laravel Telescope/Sentry + SQL logging) and nightly data integrity checks comparing prop ID counts between systems.

### Phase 5 – Validation & Cutover
1. Dual-run FastAPI and Laravel imports against a QA database; diff outputs (`prop_id`, `file_number`, `cofo`) to ensure parity.
2. Execute performance/load tests to confirm Laravel jobs meet current throughput.
3. Freeze FastAPI importer, migrate scheduling/cron jobs, and perform production cutover with rollback instructions (keep FastAPI container available for emergency use).

## 5. Data Governance & Integrity Controls
1. **File Number Table Isolation**
   - Enforce via Laravel Policy/Middleware so only the File Number import command/route can call the repository that writes to `file_number` tables.
   - Add a database constraint or trigger guard that asserts the `source_workflow` column equals `file_number_import` before insert.
2. **prop_id Master Integrity**
   - Centralize prop ID generation in a Laravel `PropIdAllocator` service calling the same SQL counter table with pessimistic locking.
   - Add automated reconciliation job comparing `prop_id` sequences between FastAPI legacy data and Laravel outputs during transition.
3. **Grouping Table Protection**
    - Mirror `_standardize_file_number` and `_normalize_file_number_for_match` for all grouping lookups; never mutate grouping rows outside dedicated admin utilities, and always derive tracking identifiers from grouping metadata when mapping imports.
4. **Retired File Tracking**
   - Maintain canonical `reason_retired` values via enum casting; reject inserts with invalid values before DB write.
5. **Audit & Observability**
   - Log every import with tracking IDs (reuse `_generate_tracking_id` pattern) and store QC suggestions, warnings, and error stacks for future forensics.

## 6. Deliverables & Next Steps
1. **Artifacts**
   - This plan (version-controlled) plus supplementary diagrams/notes.
   - A parity matrix documenting each Python helper and its Laravel counterpart.
2. **Immediate Actions**
   1. Complete the Section 3 analysis checklist and archive findings under `docs/`.
   2. Draft Laravel service skeletons for normalization, prop ID allocation, QC, and staging handlers.
   3. Define database migration scripts (Laravel `migrations/` directory) for any new audit tables or helper columns.
3. **Decision Points**
   - Choose CSV parsing library strategy (pure PHP vs. calling Python service).
   - Decide on storage for upload sessions (Redis, DB, or S3-backed chunking).
   - Align with stakeholders on rollout order (which importer to migrate first based on risk/benefit).

Once these items are accepted, we can begin implementing the Laravel modules with confidence that data integrity and workflow consistency will be preserved.
