  
# Task: Implement Handling of Complex Land File Transactions Using Temporary Holding Files

## Objective

Enhance the land management system to support complex transactions involving **merger, subdivision, and change of purpose** where the original physical files are unavailable, missing, or not yet indexed.

The solution must allow these transactions to proceed using a **temporary holding file number** while maintaining linkage to the newly created official file through its property ID.

---

# Background

In normal transactions, users select existing indexed files, and the system retrieves the corresponding file details and property information.

However, there are cases where:

* Multiple existing files were merged to create a new file.
* The old files are not indexed or cannot be found.
* The newly opened file exists and already has a property ID.
* The transaction history (merger → subdivision → change of purpose) still needs to be recorded.

The system currently cannot complete this workflow because the old files are unavailable for selection.

---

# Functional Requirements

## 1. Temporary Holding File Number

The system shall support creating a temporary **Holding File Number**.

Characteristics:

* It must be automatically generated by the system.
* It is not a normal physical file.
* It acts as a temporary container for all files involved in the transaction.
* It must persist through all stages of the transaction workflow.

---

## 2. Supporting File Number

The system shall allow the user to select the newly opened official file as the **Supporting File Number**.

Requirements:

* The supporting file must already exist in the system.
* It must have a valid Property ID.
* The Property ID of this supporting file will be the reference used throughout the transaction.

---

## 3. Merger Process

For merger cases involving missing or unindexed files:

The user should be able to:

* Create a temporary holding file.
* Associate all available information about the merged files with this holding file.
* Link the holding file to the supporting file's Property ID.

The system should not require the original files to be indexed before the merger can be recorded.

---

## 4. Subdivision Process

During subdivision:

* The same holding file created during the merger must be reused.
* A new temporary holding file must **not** be generated.
* The system must allow the user to enter subdivision details even if some subdivision files are not yet available.

The transaction chain must remain connected to the original temporary holding file.

---

## 5. Change of Purpose Process

During change of purpose:

* The process must continue using the same holding file.
* The transaction must remain linked to the supporting file and its Property ID.

---

## 6. File Type Identification

The system should distinguish between:

* Normal physical files
* Temporary holding files

Possible implementation options:

* Add a file type indicator or checkbox.
* Store a status flag (e.g., `is_temporary = true/false`).

This will allow the application to apply the appropriate workflow.

---

## 7. Conditional Workflow

The holding file workflow should only apply when:

* The transaction involves complex operations (e.g., merger + subdivision + change of purpose).
* The original files are unavailable or not indexed.

For normal transactions:

* The existing workflow should remain unchanged.
* Users should continue selecting the actual indexed files.

---

# Validation Rules

* A supporting file with a valid Property ID is mandatory before the transaction can proceed.
* The same holding file must be used across all related transaction stages.
* The system must prevent the creation of multiple holding files for the same transaction chain.
* The workflow should allow processing even when some historical files are missing.

---

# Database Considerations

Consider adding fields such as:

### File Table

```
is_temporary BOOLEAN DEFAULT FALSE
```

or

```
file_type ENUM('NORMAL', 'TEMPORARY_HOLDING')
```

### Transaction Linkage

Ensure that:

* The holding file is linked to the supporting file.
* The supporting file's Property ID is maintained as the master reference.
* All merger, subdivision, and change-of-purpose records can trace back to the same transaction chain.

---

# Acceptance Criteria

### Scenario 1: Normal Transaction

**Given** an indexed physical file
**When** a user performs a merger or subdivision
**Then** the existing workflow functions without any changes.

---

### Scenario 2: Complex Transaction With Missing Files

**Given** old files involved in a merger are unavailable or not indexed
**When** the user initiates the process
**Then** the system generates a temporary holding file and allows the process to continue.

---

### Scenario 3: Continuity Across Processes

**Given** a temporary holding file was created during merger
**When** the user performs subdivision and change of purpose
**Then** the same holding file is reused and no new temporary file is created.

---

### Scenario 4: Property Traceability

**Given** a supporting file with a Property ID
**When** all transactions are completed
**Then** the entire transaction history remains traceable through that Property ID.

---

## Priority

**High Priority / Urgent**

The implementation should be lightweight and should avoid manual database manipulation of historical files. The goal is to introduce a controlled temporary holding mechanism that allows complex land transaction workflows to proceed even when original files are unavailable.
